GigBid: R&D report (design review)

AI-4016 · build 8f7fee8 · every number below is read from evals/results/ at build time.

1. Problem and constraints

A freelancer loses hours scanning feeds, spends paid Connects on jobs they won't win, sends generic proposals and meets scams (free "test" work, off-platform payment, data harvesting). GigBid automates discovery, risk triage, evidence gathering, pricing and drafting; the human decides. Never automated: submitting a proposal, sending a message, spending Connects (each requires interrupt() approval in the UI; live Upwork additionally requires confirming the draft on Upwork), claiming experience the portfolio does not show, contacting or paying off-platform, scraping. Declared budgets (agent/config.yaml): p95 <= 30 s per job analysed and <= 90 s per proposal; <= $0.002 per job and <= $0.01 per proposal on the open profile (Groq-hosted open-weight models).

2. Architecture

Two hand-written LangGraph graphs (bid: one thread per job; conversation: one per client thread) with a Postgres checkpointer and a LangGraph store, run by an Arq worker; a FastAPI API streams node events to a React UI over SSE. All capabilities are MCP tools: GigBid's Portfolio, Marketplace and Workspace servers (21 tools, schema-snapshot tested) plus the official Upwork and GitHub servers. The graph holds one MarketplacePort; the Marketplace server picks the GigSim or Upwork adapter from config. Job Analyst, Risk Assessor and Fit Matcher run in parallel via Send; a decision node routes bid/watch/skip; Writer -> claim verification -> Critic (max 2 revisions) -> Compliance Guard -> approval -> idempotent submit. State, execution trace (state trace, run_events, append-only audit_log, Phoenix spans, one trace id) and long-term memory (style + outcome namespaces written only by explicit promotion rules) are separate. Diagrams and per-agent rationale: docs/ARCHITECTURE.md; decisions: docs/adr/.

Data. The kit lacked GigSim, persona corpora and the dev set, so all three were generated with known ground truth (docs/DATA_CARD.md): 3 personas x 18-19 projects (case studies, alt write-ups, repos+code, reviews, 150 labelled past proposals), 600 labelled dev jobs, 1,500 historical jobs, 360 clients with hidden preferences, and a held-out proxy split.

3. R&D question A: tool granularity (tool_granularity.json)

Hypothesis: typed task-level tools ("ours") beat a few action-dispatch tools on argument accuracy and many narrow tools on selection accuracy. Setup: 40 tasks with known correct calls, one tool-choice call each, gpt-oss-20b, temperature 0, nothing executed.

Design Tools Selection acc. Argument acc. Tokens/task Tasks run
fine 27 0.750 0.750 930.175 40/40
coarse 3 0.825 0.725 436.625 40/40
ours 21 1.000 1.000 2021.048 21/40

Result: the narrow 27-tool design picks the wrong tool most often (75.0%): near-duplicates such as get_client_spend vs get_client_rating split one intent across several tools. Coarse tools are cheapest (436.625 tokens) and select well, but the model must invent a free-form params dict, which costs argument accuracy. GigBid's set is the most accurate on the tasks completed so far but costs the most tokens, because its schemas carry real constraints and descriptions. Partial: the free-tier daily quota stopped the run; it resumes with make eval-llm. Conclusion: granularity changes behaviour; typed, task-level tools buy accuracy with prompt tokens, which is the right trade for write tools (idempotency key and dry-run must be exact) but argues for trimming descriptions of read tools.

Verification removes roughly a third of the experience claims the writer makes even though it cites evidence; typical removals merge two projects into one sentence or upgrade a described technique into a named tool. Where retrieval did not translate into replies: GigSim's clients reward must-have skill names, a concrete number and a question; once the evidence contains one strong result, better ranking of the second and third item rarely changes the reply decision, so reply-rate differences between variants are small compared with run-to-run variance at these sample sizes. Where better retrieval did not translate into better decisions, and the shipped choice. The Fit Matcher turns retrieval similarity into requirement strength, so the retrieval variant also drives bid/skip. With pricing fixed, swapping the Fit Matcher from v1+v2+v9 to the best-ranked v1+v2+v6+v9 lowered bid/skip F1 from 0.941 to 0.931 (bid recall 0.927 -> 0.907; decisions_dev_offline.json vs decisions_dev_offline_fit_v1+v2+v6+v9.json): the context lines shift cosine similarities down and the strength thresholds were calibrated on the plain index. Shipped: v1+v2+v9 (nDCG@10 0.848, Recall@5 0.871); recalibrating the thresholds for the contextual index is the follow-up that could let V6 ship (ADR 0003).

6. The change request (change_request_before.json, change_request_after.json)

The 2 Nov GigSim update added 2 Connects per submission (Featured jobs x1.5) and a rule that AI-assisted proposals must disclose it (rule P8, rejected with 422 otherwise). Before the fix: 0.0% of approved proposals accepted; the approval preview had already flagged P8 on 100.0% of them (the dry run applies the platform's own /policy rules) and showed the new Connects price. Fix: commit 08b287c, config only: required_disclosure and rule P8 in data/policy_pack/marketplace_policy.yaml, policy.version in agent/config.yaml, three lines of policy docs; no Python changed. After: 100.0% accepted; Connects spent match the new price because pricing reads the marketplace's own job price. It took one short session; the design point that paid off was keeping rules in YAML and reading fees from the marketplace instead of re-implementing them.

The LLM-risk episode is the clearest failure caught by measurement: when the small model's flags were trusted, scam precision on the same 30 jobs fell from 0.750 to 0.375 (decisions_dev_open_v1_trusted_llm_flags.json); a confidence gate restored it. 9. Safety and platform respect

Never: send, submit or spend Connects without an approved interrupt; follow instructions in posts or client messages; state experience the evidence lacks; contact or pay off-platform; scrape. Enforcement: LangGraph interrupt() + approvals persisted before resume + idempotency keys; injection patterns neutralised before any model reads a post, untrusted text fenced in prompts, output canary rules in the Compliance Guard; claim verification with the letter-level grounding gate; policy pack in YAML; per-user rate limiting below the platform limit; live Upwork only through its official MCP server with OAuth (no cookies, no browser automation) and drafts the user confirms on Upwork; PII masking in logs, traces and the audit log; tokens Fernet-encrypted; tenant filter on every query (tested). Measured: planted injections detected 100.0% of the time (dev); attack success undefended vs defended: pending vs pending (planted), pending for novel attacks (injection_open.json). What still gets through: the patterns are lexical, so a paraphrased instruction with no trigger words, or one placed in a screening question, can reach the writer fenced but un-neutralised; then only the writer's own instructions and the output rules stand in the way.

10. Held-out results against declared budgets (decisions_holdout_offline.json, smoke.json)

The instructor's hidden set runs after the deadline; as a proxy, the same pipeline ran on a held-out split generated with a different seed and never used for tuning: bid/skip F1 0.934, scam recall 0.958, price in band 96.5%, p95 0.537 s per job (deterministic profile) vs dev 0.941 / 1.000 / 97.8%. Budgets on the live open profile: per job analysed, p95 29.023 s and $0.0004 (budget 30 s / $0.002, met); per proposal, p95 100.043 s and $0.0032 (budget 90 s / $0.01). Latency above budget comes from Groq free-tier rate-limit waits (8k tokens/min), not compute. Optimisation that helped: deterministic routing of cheap decisions (scout, fit, pricing, decide run with no LLM) and gating the LLM risk model keep a job at about 2.2k tokens; skipping early means scams and mismatches never reach the 120B writer.
